# 0002 — 文件夹中心数据库（.pt/data.db）替代 XMP 旁车持久化识别结果

## 状态

已接受（设计阶段，随识别功能落地实施）

## 背景

集成鸟类识别（YOLO 检测 + 鸟种分类，移植自 pica）时，识别结果（鸟种名、置信度、检测框、状态）需要持久化。应用已有的标记（Rating/ColorLabel/Flag）走 XMP 旁车文件，识别结果第一反应是搭同一趟车。

讨论中否决了 XMP 路线：识别是批量型操作，几乎每个 Capture 都会产生结果，意味着照片文件夹里会出现与照片等量的 `.xmp` 文件。本应用的用户存在**直接读取硬盘或相机存储卡**的使用场景，大量伴生文件对这些用户不可接受。

同时，既有 `ExifCache` 的 `.pt-cache.db` 裸放在照片文件夹根目录（WAL 模式下连带 `-wal`/`-shm` 共 3 个散落文件），这一既有设计同样需要修正。

## 决策

每个照片文件夹一个 SQLite 库，收进隐藏式子目录：

```
{folder}/.pt/data.db
```

库内三类表：

| 表 | 性质 | 内容 |
|---|---|---|
| `exif_cache` | 缓存 | 既有 EXIF 缓存（可从源文件重算） |
| `xmp_cache` | 缓存 | 既有 XMP 缓存（可从旁车重算） |
| `recognition` | **真相** | 识别结果：相对路径键 + 鸟种名/置信度/检测框/状态 |

记录键为**主显示文件相对文件夹根的路径**（正斜杠归一化）。DB 文件位于 `{folder}/.pt/` 内部，其位置本身就是相对路径的锚点，物理上不存在 pica 式"相对谁"的歧义。

打开逻辑：优先 `.pt/data.db`；发现遗留裸 `.pt-cache.db` 时 rename 迁移（同文件夹必同设备）后删除旧文件。

**契约：任何"清理缓存"类操作只能清 `*_cache` 表，绝不可触碰 `recognition` 表。** 缓存可删，真相不可删。

## 被否决的选项

### 选项 A：XMP 旁车 `pt:*` 属性

与 Rating/Flag 同一机制，网格填充链路现成。

- 否决原因：识别结果的体量是"每张照片一条"，文件夹会出现等量 `.xmp` 伴生文件；用户直接读硬盘/存储卡的场景下不可接受

### 选项 B：pica 式 per-folder JSON

- 否决原因：pica 已证实三大缺陷——路径格式歧义（相对/绝对假设自相矛盾）、文件操作后记录陈旧、应用内第二种持久化约定

### 选项 C：应用级中心 SQLite

- 否决原因：以绝对路径为键，用户在应用外移动文件夹即全库失联；需要一套不存在的失效/对账机制

### 选项 D：`.pt/` 内两个文件（cache.db + recognition.db）

物理隔离缓存与真相，更防呆。

- 否决原因：用户明确要求复用单一 DB 文件；以"表级边界契约 + 表命名显式区分"替代物理隔离

## 理由

1. **文件夹是可移植单元**：`.pt/` 位于文件夹内部，整个文件夹被用户拷贝/搬移（包括存储卡 → 硬盘）时 DB 跟随，相对路径键全部保持有效
2. **侵入性可控**：一个点前缀目录替代裸文件 + WAL 散兵，直读硬盘的用户最多看到一个文件夹
3. **scanner 零改动**：现有 scanner 为 `max_depth(1)` 单层扫描，`.pt/` 内容天然不会被扫入；目录本身被扩展名过滤
4. **复用既有机械**：rusqlite（bundled）与 `rusqlite_migration` 迁移框架已在 workspace 中使用，合并只需追加迁移

## 影响

- 正：识别结果与文件操作（ops 移动/复制/删除）的同步点明确——ops 操作时按相对路径更新/删除 `recognition` 行
- 正：网格鸟种标签/筛选的读路径 = 打开文件夹时一次 SQLite 查询，无需逐文件读旁车
- 负：应用外的文件改名/移动会使对应记录失联（所有非旁车方案的共性代价；相对路径键把影响限制在单个文件，文件夹整体搬移不受影响）
- 负：`.pt-cache.db` → `.pt/data.db` 的迁移逻辑需长期保留（或约定版本窗口后移除）
- 约束：递归扫描若未来支持，相对路径键天然扩展（`子目录/DSC_0001.jpg`），schema 无需变更
